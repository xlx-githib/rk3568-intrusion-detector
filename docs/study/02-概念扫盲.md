# RKNN 端侧 AI 概念与项目定位（study/02）

> 说明：本文面向项目文档读者/后续学习者，讲清本项目涉及的几个核心概念，以及本项目在"端侧 AI"里的位置。
> 文中的"笔者认为"表示个人观点，供参考。

---

## 1. 本项目用的模型：scrfd 与 yolov5 不是一回事

- **scrfd**：人脸检测模型，输出人脸框 + 5 个人脸关键点（眼睛/嘴角）。只认人脸。
- **yolov5s**：通用目标检测，COCO 80 类，包括本项目关注的 `person`(0)、`car`(2)。

> 项目早期用 scrfd 只是在真机上验证"RKNN 推理链路是否打通"，与项目最终算法无关；
> 本项目的检测算法是 **yolov5s**（只取 person/car 白名单）。

---

## 2. 什么是 YOLO

YOLO（You Only Look Once）是一种**单阶段目标检测**算法：
输入整张图，一次前向，直接输出"检测到了什么（类别）、框在哪（x1y1x2y2）、置信度多少"。

需要理解的关键点：

| 概念 | 含义 | 为什么与本项目相关 |
|---|---|---|
| 单阶段 vs 两阶段 | 两阶段(R-CNN 系)先找候选框再分类，慢；YOLO 端到端一次出结果，快 | 实时检测必须快，才能跑视频流 |
| 网格 + anchor | 图被切网格，每格预测若干"先验框"的偏移量 | 后处理解码的输入依据 |
| **多尺度输出** | YOLOv5 有 3 个分支，stride 8/16/32，分别负责小/中/大目标 | 这就是 RKNN 模型"输出 3 路"的原因 |
| 后处理 | 解码框 → 置信度过滤 → NMS(去重叠框) | 模型原始输出不能直接用，必须后处理 |
| 模型后缀 s/m/l/x | small/medium/large/xlarge，s 最小最快 | 本项目用 yolov5s，保证板端实时性 |

**YOLO 与项目的关系（一句话）**：YOLO 负责"看见画面上的人/车在哪"，项目业务层负责"这些人/车进没进警戒区、要不要告警"。

```
摄像头帧 → yolov5(NPU) → 框列表[(person,0.85,x1,y1,x2,y2), ...]
                                    ↓
                      业务层：框底部中心是否落在 ROI 内
                                    ↓
                      状态机：进入 → 滞留告警 → 离开解除
```

## 3. 什么是"端侧 AI"（Edge AI）

端侧 AI = **推理在设备本地完成，不把数据上传云端**。

| | 云端 AI | 端侧 AI（本项目） |
|---|---|---|
| 数据流向 | 设备采集 → 上传云端 → GPU 算 → 结果回传 | 本地采集 → 本地 NPU 算 → 本地反应 |
| 优点 | 模型可很大 | 低延迟/隐私/不依赖网络 |
| 缺点 | 依赖网络、延迟高、视频隐私外泄 | 算力受限，模型需量化裁剪 |

RK3568 能跑端侧 AI，靠的是片内 **NPU（神经网络处理器）**。瑞芯微把模型转成 NPU 专用格式 `.rknn`，并量化成 **int8** 以提升速度。

端侧 AI 的完整链条：
```
PC 训练模型 → 量化/转换(.rknn) → 部署到设备 NPU → 上层业务应用
```
> 本项目明确只做**后半段**（部署 + 业务），不训练模型。RK3568 NPU 约 0.8 TOPS@INT8。

## 4. 项目定位与技术要点（含笔者的个人观点）

笔者认为，本项目的价值不在于"检测能跑通"（官方 demo 也能），而在于把端侧 AI 能力**工程化**成一个可演示的安防业务产品。具体技术要点：

1. **端到端业务闭环**
   V4L2 采集 → NPU 推理 → ROI 判定 → 告警截图 → socket 上报 PC，是可演示的完整链路，而非单点 demo。

2. **四线程流水线架构**
   Capture / Infer / Business / Output 四线程 + 有界队列解耦 + 队列满丢最旧帧（保实时）+ `shared_ptr` 流转避免拷贝。
   解决的核心矛盾：**采集快、推理慢，如何不互相阻塞**。

3. **RKNN 端侧部署的真实经验**
   int8 量化、RKNN C API 主流程，以及真机才遇到的坑：MIPI 摄像头出图需要 ISP + rkaiq(3A) + sensor tuning 三者匹配、NV12 格式协商、NPU 设备权限、runtime 库版本选择等。

4. **业务层：ROI 判定 + 事件状态机**
   以"检测框底部中心点是否落 ROI"判入侵，用连续帧计时近似滞留时长，并**明确交代第一版的取舍**：
   用帧级近似代替多目标跟踪，多人同时进出会近似合并（后续可用中心点 IoU 关联升级）。

5. **产品化要素**
   全部参数走 `config/intruder.conf`；告警截图与日志存盘；TCP socket 上报 + PC 上位机 `host/receiver.py`；一键 `build.sh/run.sh`；每日开发日志 `docs/devlog/`。

> 笔者认为，本项目真正的差异化在于把"单片机/驱动思维 + Linux 多线程/网络功底"结合到"嵌入式 Linux + AI 部署"上，覆盖了从采集到上报的每一环，而不是仅停留在某个 demo 层面。
