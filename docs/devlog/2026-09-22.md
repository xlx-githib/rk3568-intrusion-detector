## 遇到的问题 / 怎么解决的
- **参数热更新怎样不破坏流水线**：不用锁，改为"原子参数 + 版本号"——控制台只写、Business 线程比对
  `version` 后统一应用（`setRoi/setStaySec/setLeaveConfirm/setThresh`），控制路径与数据路径解耦。
- **控制台不能阻塞主流程**：独立线程 + `poll(stdin, 200ms)` 超时轮询，兼顾"可交互"与"可退出"。
- **配置回写怕破坏注释**：`save` 只替换自己管理的 9 个键，其它行原样保留；`reload` 只认这些键。

### 迭代2 踩坑
1. `mpph264enc` **无 `bitrate` 属性** → 属性名是 `bps`（Rockchip 插件与常规 gst 插件不同）；默认不加编码参数
2. RTP 环回 `not-negotiated` → `rtph264depay` 后**必须接 `h264parse`**；`udpsrc` 的 caps 需含
   `media/clock-rate/encoding-name/payload` 完整字段
3. **UDP 无“流结束”通知** → 接收端会一直等，需 SIGINT/超时收尾
4. **`/dev/video0` busy + 5000 端口被占** → `adb shell "cmd"` 是**非交互**执行，`Ctrl+C` 只中断 Ubuntu 端的
   adb 客户端，**板上的 gst-launch 变孤儿进程**继续占资源。教训：跑前/跑后 `killall -9 gst-launch-1.0`，
   或先 `adb shell` 进板交互再运行
5. **播放器 `non-existing PPS 0 referenced`（根因）** → `gst-inspect-1.0 mpph264enc` 显示 `header-mode`
   默认 `0=first-frame`（**只在第一帧发 SPS/PPS**），流式播放器从中间接入拿不到参数集。
   修复：`mpph264enc header-mode=1` + `h264parse config-interval=1`
6. VLC 对 “MPEG-TS over TCP” 支持差（MRL 语法苛刻，`udp://@0.0.0.0:5000` 不被接受）→
   验证优先用 `ffplay -f mpegts tcp://<板IP>:5000`
